# AGENTS.md — starlance-replay-uploader

## Purpose

Go system-tray app that watches every SC2 multiplayer replays folder on the machine (one per account) and auto-uploads new `.SC2Replay` files to the ladder backend. UI-first: never add terminal-only flows.

## Rules

- **The match cue is CC0.** `app/assets/sounds/match-found.wav` is the OpenGameArt
  "16-bit success sound" (CC0, no attribution required), converted to mono 44.1 kHz
  PCM WAV. It plays from the app through the platform player (`playSound`), never
  from the webview, because WebKitGTK refuses `play()` without a user gesture even
  for a click. Do not put Blizzard audio assets in this repo: the uploader is a
  standalone binary, so extracted game audio would be redistribution.
- **Two accounts on one machine.** `-profile <name>` moves auth, settings, dedup
  records and the log into `appDir/profiles/<name>`, so a second instance holds a
  different Battle.net login; the window title appends the profile name.
  `-prefix <wine prefix>` keeps that instance watching only its own prefix's replay
  folders, so a two-account test cannot upload the other account's games. Existing
  replays are never backfilled, so old files in a watched folder are inert.
- **A greyed region chip explains how to make it available.** Unverified regions render
  grey, and clicking one says "Log in to StarCraft II on the {region} server once with
  this account to create a profile, then check again." Never ask the player to link a
  second Battle.net account for a region: one account can hold a profile per region, and
  the backend probes that (`{region}.api.blizzard.com/sc2/profile/user`).
- **A star on a region chip is one preference, not a set.** With two or more
  regions selected, each chip grows an attached star (spec 2.31.0
  `preferred_region`); starring one region un-stars the previous one, so the
  star behaves like a radio choice. A region both players name is always played,
  otherwise a region one player names, otherwise pairing stays random. The choice
  lives in `sl.preferred` as a single region string, stars are hidden when only
  one region is selected (the intersection is already fixed), and a stale
  preference outside the selected set is dropped by the client and ignored by
  the backend.
- **The match moment is one overlay, not a card in the page.** `app/frontend/dist/index.html`
  `#mmModal` covers the window: Accept/Decline with a 60 s draining bar and no opponent
  name (nobody has agreed yet), then Waiting, then the instructions with Region (flag), Map (with the backend map preview) and
  Host as the three leading facts, a map preview image, and at most three short
  steps for the host or the guest. Lobby names are NOT shown: the invite is the
  only join path, so nobody has to read out a lobby. Decline
  calls `POST /matches/{id}/draft/decline` (voids the match, requeues an opponent who
  already accepted, no penalty). The window has no push channel, so
  `setInterval(refresh, 2000)` is what turns queue into match and accept into
  instructions; never remove it.
- **Player-facing copy follows the StarLance copy rules.** Name things in full
  ("the StarLance Replay Uploader"), no em dashes, no system as the actor (automation is a state or a result:
  "results are read from replays", "your rating is calibrated in roughly 10 games"), use
  "uploads" never "sends", and open instructions with the action verb. Window strings live
  in `app/frontend/dist/{index.html,app.js}`; there is no build step for them.
- **No hover tooltips.** Never add `title=` attributes, JS `title` assignments, or
  hover popovers to the window UI (`app/frontend/dist/{index.html,app.js}`): a fact the
  player needs belongs in visible copy or a button label, and an `aria-label` may carry
  it for screen readers. Hover-only text is undiscoverable (touch, keyboard), invisible
  in screenshots, and reads as a band-aid over a label that should say the thing.
- **A desktop toast is one thought.** The notification daemon clips the body at roughly
  two lines, so a toast title stays under ~25 characters and the body under ~45: no paths,
  no URLs, no raw Go errors, no second instruction. Detail belongs in the window (or the
  log); the toast names the state and, if needed, the one place to fix it. Never point at a
  tray row that does not exist (login lives in the window, not the tray).
- **One window, three tabs, slim tray.** The window is the client: `Play` (race row, region chips, Find match / Stop queue, status; `data-tab="ladder"` in the markup), `Map bans` (one account-wide pool as map-preview tiles - the grid columns follow the pool size - capped at the season allowance, saved through `GET/PUT /me/map-bans` and applied by the backend's draft to every match regardless of race; logged-out shows a login card that jumps to the Ladder tab), and `Settings` (account, Log in/Log out, replay folders showing the full path: click a row to open it or remove it, Add folder, Start with system, version, Check for updates, Close uploader). The tray stays a fast path: status row, attention fix row, Open the StarLance App, Quit. Windows build uses `-H windowsgui`; no console. The mod is chosen in the lobby's mod list, never installed; finding a match is not a setup step.
- **Zero-paste auth (device flow).** Login = the window's Log in (Ladder login screen or Settings) → the app requests a device code (POST `/api/uploader/authorize/start`) → the browser opens the returned `authorize_url` on `starlance.club`, auto-approving for logged-in sessions → the app polls POST `/api/uploader/authorize/poll` (428 = pending) until the token is issued, then persists it in the 0600 auth token file. There is no localhost callback and no manual-paste path. Never display the token in UI or logs.
- **Persisted state across restarts:** all state (auth token, settings.json with backend URL + replay folder, records.json dedup index, uploader.log) lives in the per-user app dir — `%APPDATA%\StarLance\uploader\` on Windows, `~/Library/Application Support/StarLance/uploader/` on macOS, `~/.config/starlance-uploader/` on Linux — with user-only permissions (files 0600, dir 0700). Never read or write state next to the binary; the per-user app dir is the only state location. Replay folders: auto-detection returns EVERY account subtree (`Accounts/<account>/[<toon>/]Replays/Multiplayer`, most recent first) and re-runs at every startup so a new alt account is picked up with no config edit; `replay_path` in settings only adds one explicit extra folder (set from the tray picker); on total detection failure ask via folder picker, never guess. A picked folder is added to the watched set, never replacing it. Detection covers each platform's real layouts: Windows uses the known Documents folder (OneDrive-relocated included); macOS adds Whisky/CrossOver prefixes; Linux walks `~/.wine`, Lutris `~/Games`, Heroic, Bottles, native/`.steam`/Flatpak Steam `compatdata` and every extra Steam library in `libraryfolders.vdf`, and every prefix is scanned through all of `drive_c/users/*` because the Wine user name is not predictable. Pin a new layout with a fake-HOME test.
- **Never backfill.** Only replays that appear while the uploader is running and logged in are uploaded; files already in the folder are never uploaded (no initial scan, no login-time dialog, no manual upload control in the app). A genuinely missed game is uploaded from its match page on the website; the app keeps the automatic rule strict.
- **StarLance pre-detection is fail-open, never a gate** (probe.go + modcheck.go): before uploading, the replay's 40-byte `s2ma` content handles are scanned out of the decompressed `replay.details` (schema-free MPQ read, no SC2 build knowledge - only Blizzard's s2protocol in the backend parses game data) and compared - by 64-hex content tail (the last 32 bytes of the handle, the depot content key; the region-coded 8-byte prefix never matches across regions) - against the union cache of every hash ever seen in the public `GET /mod-versions` `accepted_hashes` **and `map_hashes`** (bound map tails). Map markers are what pass the first game after a mod publish through to the backend's depot-verified auto-adoption (decision 2026-09-08). A replay with no known StarLance marker is skipped silently (activity line, no toast) and still feeds the double-queue gate. An empty cache, failed refresh, unreadable MPQ, or handle-free details ALWAYS upload as before - the probe only saves a roundtrip and must never block a legitimate game. Outdated-but-known mod hashes keep uploading so the backend's precise "mod is outdated" toast survives.
- **Start with system** is a window Settings toggle (startup*.go), not a config form: XDG autostart entry on Linux, HKCU Run key on Windows, LaunchAgent plist in `~/Library/LaunchAgents` on macOS (`launchctl bootstrap` into `gui/<uid>`). The registration is per profile and replays this instance's `-profile`/`-prefix` flags (`loginArgs`): macOS gets its own label/plist, Linux its own `.desktop` file, Windows its own Run value, so two accounts never overwrite one entry and a login launch resumes the account that enabled it instead of a bare default-profile app. The platform registration is attempted before the Config field is persisted, so the checkbox never claims a state the system does not honor, and the enabled check compares the full command line against this binary and profile (another entry never lights the checkbox). The registered path is stable because the first launch installs the app in a per-user location (next bullet).
- **The app installs itself once and runs from a stable per-user path.** Players launch the downloaded file straight from Downloads, or a zip extracted to the Desktop, and browsers/cleanup tools delete those folders; a desktop entry, login registration, or updater left pointing there is how the app silently stops starting (and a quarantined macOS app is also subject to App Translocation). On first launch `relocateIfNeeded` (`relocate.go` + `relocate_<os>.go`) copies the binary to `%LOCALAPPDATA%\Programs\StarLance\sc2-replay-uploader.exe` on Windows, `$XDG_DATA_HOME/starlance-uploader/sc2-replay-uploader` on Linux, or `~/Applications/StarLance App.app` on macOS (the bundle is copied whole with `copyTree`; `/Applications` is already stable), then starts that copy detached with `-takeover-from=<pid>` plus the user's flags verbatim (`takeoverArgs`) and returns from `main`, so the two instances never run at once. An existing install is never overwritten (it may be running; self-update owns replacing it), and every failure falls back to running in place instead of refusing to start. `-portable` and dev builds never install a copy (dev binaries would copy `go test`/`go run` temporaries). Windows also writes a Start Menu shortcut (`shortcut_windows.go`): `%APPDATA%\Microsoft\Windows\Start Menu\Programs\StarLance App.lnk` (profile-suffixed name, same `-profile`/`-prefix` arguments), created with in-process `WScript.Shell` COM and `runtime.LockOSThread` (never PowerShell, never a console window), rewritten only when missing or older than the binary. Linux already gets its app-menu entry from `installDesktopIntegration`; macOS ships the app bundle.
- **Launch-at-login self-heals at startup.** `reconcileRunAtStart` (after `LoadConfig`) treats the OS registration as truth: saved "on" with no entry turns the setting off (honoring a removal made in the OS, never re-adding it underneath the player), an entry that launches an older path is rewritten to the current binary, and a write failure turns the setting off so the checkbox never lies. It reads the entry back with `firstExecArg` (Linux `Exec=`), `firstCommandArg` (Windows Run value), and `plistFirstProgramArg` (macOS plist), so the comparison covers the binary path, not just "some registration exists"; an unparsable own entry is rewritten rather than treated as removed.
- Windows notifications by severity (notify_windows.go): problems are topmost MessageBoxW warnings raised with MB_NOFOCUS so they never steal keyboard focus (the player may have re-queued); the old focus-grabbing box remains only for fatal startup errors. Infos are Action Center toasts raised through PowerShell `-EncodedCommand` (registered PowerShell AUMID - an unregistered custom AUMID is dropped by some builds; cgo stays off). A failed info toast logs quietly; it is never modal.
- Handle rejection reasons from the backend (mod hash retired, map mismatch) as notifications, not silent failures. Notice severity: `no_pending_match` (a StarLance-mod game played outside the queue) is NoticeInfo with no attention state - expected behavior, never a modal warning; every other rejection is NoticeProblem + StatusAttention. A retryable failure that exhausts the retry budget (network/5xx) is never silent either: attention + problem toast pointing at the match-page manual upload, because the replay is never retried (never-backfill). Every successful upload notifies with the match outcome ("Win vs X · map") - the post-game "did my game count?" answer.
- **The pending match is followed to resolution (pending.go).** A 202-accepted upload is not the end: a single poller (20s interval, 30min cap) discovers the pending match on GET /queue/status (the 202 carries no id), then polls the public GET /matches/{id} until it leaves "pending" and toasts the same matchNotice outcome as a resolved upload - so the first uploader gets the answer even when the opponent's replay confirms the match. Fail-soft throughout: errors keep polling, a vanished/unfindable match goes quiet and leaves the outcome to the site's notifications. The tuning vars are snapshotted at poller start so a mid-run swap is never read racy.
- **Player words in every status surface, machine codes nowhere.** The attention state's reason is the one-phrase player version (rejectionShort in uploader.go), not the raw backend code - it feeds the tray tooltip and the activity dialog; activity-feed failure lines append the same short reason (or "StarLance unreachable") so "See what's wrong" answers why at a glance. Session-expired and logged-out-startup toasts say the consequence ("games played until then will not count - upload them from their match page on starlance.club"), and a voided match gets a "Match not counted" toast like held/draw/win/loss.
- The watcher tolerates up to 10 consecutive `os.Stat` failures before dropping a file (AV scan, create-pending race); a transient failure must never drop a replay.
- `GOOS=windows GOARCH=amd64` and `GOOS=linux GOARCH=amd64` builds must both work, `CGO_ENABLED=0`. The queue window is a Wails app embedded from `app/frontend/dist` and runs in the same process as the tray (Wails owns the main goroutine, the tray runs alongside). There is no separate window mode. Closing the window hides it; Close uploader in the window or Quit in the tray ends the process. Windows needs WebView2 (present on Win10/11 and bundled in current images); a Linux window run needs cgo plus GTK/WebKit, so the cgo-free Linux build keeps the tray working but cannot open the window. To run the window locally, build with cgo in the Fedora container (`-tags production,webkit2_41`), mounting the repo with `:Z` and running the container as root; `--userns=keep-id` breaks `dnf` (non-root) and a failed install silently leaves the previous binary in place. Launch the result with `DBUS_SESSION_BUS_ADDRESS`, `XAUTHORITY` and `DISPLAY` set, or the tray panics with `dbus: connection closed by user`.
- **The Windows executable carries the icon as a resource.** Explorer, the Start menu and the taskbar read the `.exe` itself, so `app/rsrc_windows_amd64.syso` (compiled from `app/assets/win/rsrc.rc` + `icon.ico` by `make icon`, all generated from the shared `app/assets/sl-logo.png`) is committed and links into every Windows build; without it the executable shows the generic blank icon. Regenerate (`make icon`) only when the logo changes, and keep the `.syso` committed so CI needs neither ImageMagick nor mingw.
- **Linux taskbar icon comes from the desktop entry, not the window.** Wayland has no per-window icon: the compositor matches the window's app_id (`linux.Options.ProgramName`, which is `linuxAppID` = `starlance-replay-uploader`) to a `.desktop` entry and reads that entry's `Icon=` key. Release zips are a bare binary, so nothing installs those files; `installDesktopIntegration` (`desktop_linux.go`, called at startup) writes and refreshes the entry plus the 256px icon in the user's XDG data dir, rewrites only changed content, refreshes the hicolor cache, and removes the stale `StarLance.desktop`/`starlance-uploader.desktop` entries only when their icon key proves they are ours. Missing this paints KDE's generic Wayland-logo fallback (the white W on a yellow circle). `linux.Options.Icon` still covers X11; the window icon is the same mark pre-rendered by `encodePNG(256)`.
- **Every player-facing feature ships on all three platforms.** Windows, Linux and macOS are all released (`.github/workflows/release.yml` matrix; darwin needs `CGO_ENABLED=1` and runs on macOS runners because the window is Cocoa/WebKit). Platform seams live in one file per OS with a build tag (`notify_darwin.go`, `dialogs_darwin.go`, `folderpick_darwin.go`, `startup_darwin.go`, `sound_darwin.go`, `browser*.go`, `icon.go`, `relaunch_*.go`); never leave a platform on a "not supported" stub when the OS has a native answer. macOS specifics: notifications via `osascript` (strings passed as script arguments, never interpolated), pickers via `choose folder`/`choose file`, folder/open targets via `open` (not `xdg-open`), tray icon via `systray.SetTemplateIcon` (template image = alpha only; the colored artwork renders as a block) with no `SetTitle` text in the menu bar, window close hides instead of quitting (Wails `HideWindowOnClose`: macOS hides the whole app, Windows/Linux hide the window widget; tray Quit and self-update restarts call Quit directly). The macOS release also ships a `.app` zip for first install whose asset name must NOT contain the `darwin` token (the updater matches `-<os>-<arch>.zip` suffixes and would otherwise pick the bundle and fail to extract a binary); the updater replaces `Contents/MacOS/sc2-replay-uploader` inside the installed bundle.

- **Tray spinner state follows the queue, not the click.** The spinning tray icon starts when this process queues and stops whenever `/queue/status` reports anything other than `searching` (`Status()` calls `stopTraySpin`), so a queue ended on the website or by a match landing cannot leave the tray spinning. Frames are 48 PNGs at 33ms, logo at the icon's full width, ring drawn behind the mark.

- **Every player-facing update and install flow is browser-download or fully automatic in-app** (update.go, built on `github.com/creativeprojects/go-selfupdate` - the library, not hand-rolled update code; restart/takeover glue in update.go + relaunch_*.go is ours): never winget/package-manager flows, never terminal instructions, never an update prompt the player must answer. Updates check GitHub (`SC2-StarLance/starlance-app` releases: right after startup, then every 6h), verify the release asset's minisign signature (`<asset>.zip.minisig`, checked by `minisignValidator` against the embedded `app/minisign.pub`), swap through the library's `UpdateTo` (newer-version only, never downgrade), and restart silently with state intact. Update failures fail open (quiet retry), like the replay probe; dev builds never self-update. The window starts hidden and the first check picks what the player sees: the main window when there is nothing to do, or a 420x190 update card ("Updating StarLance", version, indeterminate bar) while the download runs, then "Restarting the uploader". Wails v2 is single-window, so the card is the same window resized, never a second window; a failed mid-session update resizes back and clears the card. Release asset names (`sc2-replay-uploader-<os>-<arch>.zip` plus a `.zip.sha256` for manual checks and a `.zip.minisig` for the updater) are the contract detected by the library - change the workflow and update.go comments together. Windows releases also carry a bare `sc2-replay-uploader-windows-amd64.exe` for the website's one-click download; it is never updater payload, so the updater pins `Config.Filters` to the zip (`pinnedAssetPattern`), because the library's suffix matching would accept either asset and pick whichever the release lists first.

- **A self-update restart uses the executable path captured at startup, never one resolved after the swap.** `os.Executable()` follows the running file, and the update library renames it to `.<exe>.old` during install (Linux and macOS too, not only Windows), so resolving it after `UpdateTo` yields a path that no longer exists and `relaunchSelf` fails with `start .../.sc2-replay-uploader.old: no such file or directory`: the app exits after promising a restart and the player has to start it again. `main` stores `launchedExe` at startup (before relocation and before any update) and `relaunchSelf` uses it. Two related rules from the same round: the watcher must not fail on an empty replay-folder set (first launch waits for the picker and the folder is added live, so `Run` idles instead of returning an error), and the shutdown goroutine loops over `ctx.Done`/`restartCh`/`watcherDone` instead of returning after the first event, because a watcher error that consumed the select swallowed the restart signal and left the update card stuck at "Restarting" forever.

## Build

```sh
make assets    # fetch pinned Blizzard artwork (required before any build)
make all       # linux + windows binaries into bin/
make build-macos   # darwin binary (needs a mac, cgo on)
make app-macos     # double-clickable .app bundle (mac only)
make test
```

Module path: `github.com/SC2-StarLance/starlance-app`. Public releases are built from this repo; the canonical release history lives on the GitHub releases page.

Layout: `app/` is the Go package and holds everything it embeds (`app/frontend/dist`, `app/assets`, `app/minisign.pub`, `app/rsrc_windows_amd64.syso`); `tools/`, `packaging/`, `docs/` and the module files stay at the root. The root file list stays short on purpose so the README and its screenshot show on the GitHub page without scrolling past a wall of source files. Build the app as `go build ./app` (a bare `go build .` no longer means anything) and keep new source files inside `app/`.

Local testing switches (dev builds only, never release builds): `STARLANCE_DEV_ASSUME_NEW_PLAYER=1` makes `Bootstrap` report no played regions, so the match card shows the "First game on <region>" / `/join StarLance` reminder for an account that already has history. Set it in the environment of a dev instance (for example a systemd user unit).

## Public repo hygiene

- **Blizzard artwork never enters this repository.** League emblems, race icons and the background image are fetched at build time by `make assets` (`tools/fetchassets`) from `SC2-StarLance/starlance-assets` at the commit pinned in `assets.lock`, with every file's SHA-256 verified. `artwork.go` embeds the same paths, so a plain `go build` fails until the fetch has run. Update the pin only deliberately: bump `assets.lock` in the same commit that needs the new art.
- **No real player data in the tree.** Tests use a synthesized replay built by `buildMPQ`/`fixture_test.go`; never commit a replay captured from a real match.
- **Release assets are signed.** `tools/signrelease` reads `MINISIGN_SECRET_KEY` and writes `<file>.minisig` for every release file; the updater rejects anything that does not verify. The secret key lives only in the protected `release` environment of GitHub Actions, never in the tree.
- **The app is MIT.** Contributions arrive as issues; this project does not take pull requests. The StarLance name and logo stay outside the license. Third-party notices live in `NOTICE`, privacy facts in `PRIVACY.md`, security contact in `SECURITY.md`.
